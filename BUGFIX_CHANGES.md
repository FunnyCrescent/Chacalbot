## ИТЕРАЦИЯ 12 — фиксы живого тестирования: TypeError на /dndcychwyn, markdown → HTML, base_url

### /dndcychwyn падал: «TypeError: process_with_db_bot() got an unexpected keyword argument 'session_id'»

**Проблема (реальный лог):** и кнопка выбора сеттинга, и ручная
`/dndcychwyn arthurian_chivalry` падали с ошибкой генерации/старта. Пять точек
вызова (`world_cmds.py:840`, `generators.py` ×4 — terrain/weather/world/living
world) передают `session_id=`, а обёртка `process_with_db_bot(raw_text,
context="")` его не принимала.

**Решение:** обёртка получила параметр `session_id: str = ""` и пробрасывает
его в `process_db_bot`. Бонус-эффект: раньше через обёртку
`self._current_session_id` ВСЕГДА оставался пустым — а его читает
`moder_ai_dispatch_roll` для доступа к БД (запрос бросков через кнопку в этих
флоу был сломан). Теперь промпт DB-Bot берётся из копии сессии
(`md_store.get_prompt`), как и у остальных флоу.

### «Md разметка, которую телеграм не принимает. Должно быть HTML»

**Проблема (репорт: «✅ \*\*О_О\*\* присоединился!»):** 9 точек отправляли в
Telegram строки с markdown без конвертации: звёздочки видны как есть (без
parse_mode), легаси `parse_mode="Markdown"` (депрекейтед), а в
character_cmds.py — ручной `blocked.replace("**", "<b>")`, который заменяет
открывающие и закрывающие `**` ОДИНАКОВО на `<b>` → незакрытый тег «<b>...<b>»
→ Telegram отбрасывает ВСЁ сообщение (400 can't parse entities).

**Решение:** все точки переведены на штатный `md_to_html()` +
`parse_mode="HTML"` (экранирование → конвертация → валидация баланса тегов):
lobby_cmds (подтверждение входа `/ymuno`, отказ биллинга), narrator_cmds
(включение перевода), service_cmds (подсказка `/rhwymo` вне ЛС), character_cmds
(отказ смены персонажа), plugins/billing (ЛС-гейт, исчерпание токенов, drained-
notice, /ychwanegu использование+успех, admin-лог, billmode-меню). Остальные
отправки и так шли через `send_safe` (конвертирует сам) — проверено AST-сканом
всех точек отправки.

**Регрессионный тест:** `tests/test_iter12.py::TestNoRawMarkdownSends` —
AST-скан репозитория: ни одна прямая отправка (reply_text / edit_message_text /
send_message / …) не должна содержать markdown-литералов в обход md_to_html /
send_safe.

### config.json: «base_url» пустым — деплой без LM Studio больше не ловит connection refused

**Проблема:** в config.json был захардкожен `api.base_url:
"http://localhost:1234/v1"` (локальный запуск из ИТЕРАЦИИ 8) — на сервере без
LM Studio каждый LLM-вызов упирался в отказ соединения ещё до перебора
провайдеров.

**Решение:** `"base_url": ""` — теперь сервер НЕ задаётся в config.json:
при заполненном `LLM_PROVIDERS` в .env используются base_url/ключи/модели из
него (с авто-переключением ИТЕРАЦИИ 11); без LLM_PROVIDERS — `OPENAI_BASE_URL`
из .env. Загрузчик трактовал пустую строку правильно с самого начала —
зафиксировано тестами (пустая → env, непустая → перекрывает env).

**Тесты:** tests/test_iter12.py (19) — проброс session_id (+_current_session_id),
md_to_html на всех исправленных текстах (включая враждебное имя игрока
«\<b\>&script\</b\>»), поведение api.base_url ("" / непустая / отсутствует),
AST-скан «сырого markdown». Итого 360/360.

## ИТЕРАЦИЯ 11 — авто-переключение провайдеров на гео-блоке + creu через общий клиент

### Гео-блок Google валил /cymeriad: «вердикт: ERROR. API 400: User location is not supported»

**Проблема (реальный лог):** у пользователя 4 API в `LLM_PROVIDERS`, но проверка
листа падала с `400 FAILED_PRECONDITION: User location is not supported for
the API use.` — и перебор НЕ запускался. Причина: по ТЗ Раздела 8 ответ 400/404
считался ошибкой ЗАПРОСА («чужой провайдер вернёт ту же 400») и уходил наружу
без переключения. Для Google Gemini это неверно: гео-блок, невалидный ключ,
отключённый биллинг и suspended-аккаунт приходят именно как 400/403/404, но
означают, что провайдер не обслужит НИ текущую, НИ любую другую модель.

**Решение:** классификация дополнена паттернами тела ответа
(`config_legacy.PROVIDER_LEVEL_ERROR_PATTERNS`, сравнение case-insensitive по
сырому телу): `failed_precondition`, `user location`, `location is not
supported`, `api key not valid`, `permission denied`, `billing`,
`insufficient_quota`, `suspended` и др. Такой ответ → `_ProviderSwitch` с
новым флагом `provider_level=True` — цикл chat()/embed() пропускает ВСЕ
оставшиеся модели мёртвого провайдера и сразу идёт к следующему. 401/402
тоже стали provider_level (ключ не «починится» на другой модели); 403 без
паттернов остался пер-модельным (бывает тировый доступ к конкретной модели).
Честная ошибка запроса (400/404 без паттернов — кривая схема, unknown model)
по-прежнему идёт наружу без сжигания чужих провайдеров. Дополнительно
`_parse_api_error_body` разворачивает тело-массив `[{"error": {...}}]` —
именно так Google-совместимые шлюзы возвращают ошибку (раньше пользователю
уходил сырой JSON вместо сообщения). Если гео-блокнуты ВСЕ провайдеры —
`AllProvidersExhausted` с человекочитаемой последней ошибкой.

### /creu больше не обходит перебор провайдеров

**Проблема:** `libs/creu/llm.py` делал собственный aiohttp-вызов на
фиксированный `OPENAI_BASE_URL` — без перебора провайдеров, без ретраев,
таймаут 30с. При гео-блоке/недоступности основного провайдера диалог создания
персонажа падал, хотя остальные API были рабочие.

**Решение:** `chat_completion()` переписан как тонкая обёртка над
`OpenAIClient.chat(role="creu")` — перебор `CREU_PROVIDERS → LLM_PROVIDERS →
дефолт`, retry/backoff, прокси, usage-биллинг и «средовые» переключения —
всё как у остальных ролей. Для `response_format` (json_object при генерации
персонажа) у `chat()` добавлен опциональный `extra_payload`. Поведение
fail-soft сохранено: `get_options()` возвращает `[]` при исчерпании
провайдеров, диалог /creu не падает.

### Тесты

`tests/test_iter11.py` (14): классификация паттернов (гео-тело из реального
лога, регистронезависимость, честные 400/404/422 НЕ переключаются),

## ИТЕРАЦИЯ 10 — сводное ТЗ: 8 разделов (бой/персонаж/апелляция/инициатива/рестарт/монетизация/плагин billing/провайдеры)

### Раздел 1 — бой не съедает заявленное действие игрока (промпт-фикс)

**Проблема:** переход в бой стирал/пропускал действие, только что заявленное
игроком в `Дн.`: удар игрока по гоблину или «иду искать таверну» заменялись
фразой «на тебя напал гоблин» вместо результата заявленного действия.
Это частный случай класса БАГ #4/#5 (повторы/смешение действий), не покрытый
прежним фиксом.

**Решение:** только промпт-инструкция, без технических полей (решено
пользователем; `skip_first_turn` НЕ реализуем). Новый раздел в
`MD/prompts/master.md` (и в `MD/_applied/prompts/master.md` — шипятся
синхронно): «НАЧАЛО БОЯ НЕ СТИРАЕТ ЗАЯВЛЕННОЕ ДЕЙСТВИЕ (БАГ #14)» —
прямо под блоком БАГ #4/#5. Оба примера пользователя включены как
иллюстрации: (1) удар игрока резолвится СРАЗУ в этом же раунде, ответка
гоблина — со следующего раунда; (2) внезапное нападение НПС накладывается
ПОВЕРХ результата заявленного действия («искал таверну» остаётся фактом),
а не вместо него. Правок в `Combatant`/`combat_coordinator.py` не требуется.

### Раздел 2 — нельзя сменить персонажа после создания мира

**Проблема:** защиты не было вообще: `_apply_saved_char_to_session()` и
прямой аплоад листа в группе позволяли подменить живого персонажа посреди
игры; единственная проверка — регистрация в сессии.

**Решение:** гард `_char_change_blocked()` (character_cmds.py) в ОБОИХ путях
входа: применение сохранённого листа и прямой аплоад в группе. Правило:
мир уже сгенерирован (персистентный маркер `session.current_scene`, тот же,
что использует world_gen_guard) И у игрока есть живой персонаж (hp > 0,
is_alive) → блокировка с понятным сообщением. Разрешены: новый игрок и
замена ПОСЛЕ смерти (hp <= 0 / is_alive=False). До генерации мира замена
листа свободна (игроки грузят листы до /dndcychwyn и исправляют опечатки).

### Раздел 3 — DB-Bot не одобряет апелляцию без единого хода

**Проблема:** `world_gen_guard` блокировал апелляции только до/во время
генерации мира; между «мир создан» и «первым ходом игрока» было окно, где
DB-Bot анализировал апелляцию «против истории», которой не существует.

**Решение:** дополнительная более узкая проверка СТРОГО после существующего
гарда (не замена): `has_any_round_history(session_id)` — если в истории нет
ни одной записи `entry_type="narrative"` (записи "system" вида
[DNDSTART]/[AUTO_START] ходами не считаются) → отказ с объяснением
и подсказкой сделать ход. Хелперы `is_world_created` / `has_any_round_history`
— в libs/handlers/utils.py.

### Раздел 4 — тай-брейк инициативы при равных значениях

**Проблема:** `initiative_list.sort(key=..., reverse=True)` — стабильная
сортировка оставляла порядок вставки; Мастер сказал в нарративе «Хравна
ходит первой» при равных инициативах, а система этого слова не хранила.

**Решение (выбранный «сложный» вариант — явное поле, не трюк +1/+2/+3):**
- tool-схема `dechrauymladd`: необязательный параметр `priorities`
  ({имя_участника: int}; МЕНЬШЕ = РАНЬШЕ) с инструкцией указывать только
  реально равных и только если Мастер уже сказал в нарративе, кто первый;
- `master_engine.py`: разбор/нормализация priorities + передача в
  combat_starter (с back-compat по TypeError для старых колбэков);
- `combat_coordinator.start_combat_for_participants` и легаси
  `start_initiative_combat`: python-сортировка
  `key=lambda x: (-initiative, priority)`;
- Combatant.priority — новая колонка (миграция ALTER TABLE для старых БД);
  `get_initiative_order` (SQL): `ORDER BY initiative DESC, priority ASC, ...`
  — единый порядок для боевого цикла/очередей/join_active_combat;
- в нарративе игроки по-прежнему видят сырую инициативу («оба 15»):
  priority — служебное поле, видно в логах tool-вызова, не является
  игромеханическим бонусом.

### Раздел 5 — «рестарт»-баг: консенсус игроков не меняет историю (промпт-фикс)

**Проблема:** инструмента /restart в коде НЕТ (проверено) — но Мастер под
социальным давлением консенсуса («рестарт»/«начни заново» от нескольких
игроков) реально отыгрывал откат истории.

**Решение:** раздел «АНТИ-РЕСТАРТ: КОНСЕНСУС ИГРОКОВ НЕ МЕНЯЕТ ИСТОРИЮ»
в `MD/prompts/master.md` (+ _applied): просьбы «рестарт»/«начни заново»/
«отмени это» НЕ являются командой и не влияют на историю/БД, сколько бы
игроков их ни повторило — это не голосование; реальные откаты — только
системные команды (завершить сессию и создать новую); в мире такая просьба
отыгрывается как момент сцены, без перезаписи фактов.

### Разделы 6-7 — монетизация: COMMERCIAL_MODE + плагин billing (единый публичный репозиторий)

**Архитектура (по ТЗ):** вся логика — в отдельном плагине `plugins/billing/`
(depends_on: persistence, session-core; лицензия MIT, код живёт в том же
публичном репозитории). ОБЯЗАТЕЛЬНОЕ требование «любой плагин удаляем без
краша» выполнено паттерном `get_plugin()`:
- `Bootstrap._post_init` кладёт менеджер в `application.bot_data["plugin_manager"]`;
- хендлеры достают плагин ТОЛЬКО через `get_billing_plugin(ctx)`
  (libs/handlers/utils.py) → `manager.get_plugin("billing")` → None, если
  папка удалена/выключена → проверки пропускаются, бот работает бесплатно;
- НИ ОДНОГО прямого `import plugins.*` из libs/handlers (тот падал бы
  ModuleNotFoundError'ом до discover()) — зафиксировано тестом, сканирующим
  libs/ на такие импорты; обратная зависимость lobby-session → billing
  отсутствует.

**Поведение флага COMMERCIAL_MODE (.env, true/false):**
- false/не задан: игра бесплатна ВЕЗДЕ (общий чат, ЛС, любые чаты),

### Раздел 8 — провайдер/ключ/модель: перебор БЕЗ памяти между запросами

**Формат:** Host+API = один «провайдер» с НЕСКОЛЬКИМИ моделями; пока не
перепробованы ВСЕ его модели — к следующему провайдеру перехода нет.
Конфиг: `LLM_PROVIDERS` / `<ROLE>_PROVIDERS` (.env, JSON) или
`api.llm_providers` (config.json); приоритет: <ROLE>_PROVIDERS →
LLM_PROVIDERS → config.json → одиночный дефолтный провайдер
(OPENAI_BASE_URL/OPENAI_API_KEY + модель роли — полное back-compat).

**Логика (упрощение, решённое пользователем):** НИКАКОЙ персистентности,
`provider_state.json` НЕ создаётся; каждый вызов `chat()`/`embed()` начинает
перебор ЗАНОВО с провайдера №1 / модели №1 (самовосстановление без риска
«навсегда застрять» на дорогом варианте; осознанный компромисс — дольше при
затяжном сбое первого провайдера).

**Реализация:** retry/backoff-цикл выделен в `_chat_once(provider, model, ...)`
— применяется к КОНКРЕТНОЙ паре; классификация ошибок:
- 401/402/403 → переключение сразу (ретраить бессмысленно);
- исчерпание ретраев 429/5xx/сеть → переключение;
- 400/404/422 — ошибка ЗАПРОСА, не провайдера → сразу наружу, перебор
  не продолжается;

### Тех. сообщения удаляются только ПОСЛЕ нарратива (БАГ #12 v2)

**Что было после первого фикса:** `auto_delete=15` заменён на
`_track_round_message(..., "bot_confirm")` + `_delete_round_messages` спит
`ANTISPAM_DELETE_DELAY` (2 сек) перед удалением. Но пользователь жаловался,
что тех. сообщения ВСЁ ЕЩЁ удаляются до нарратива. Причина:
- `_delete_round_messages` запускается `asyncio.create_task` сразу после
  отправки нарратива, но叙事 может идти 30+ секунд через `_send_long_blockquote`
  с retries — и task-удаление стартует «параллельно».
- `auto_delete=15` всё ещё использовался для «✅ сходил» в боевой ситуации.

**Что стало (bunker-bot pattern):**
- Создан in-memory dict `_pending_combat_messages: Dict[str, List[Dict]]`
  (как `game._discussion_messages` / `game._vote_messages` в bunker-bot).
- Все тех. сообщения боя («⚔️ Ход:», @упоминание, «✅ ... ⚣ Разрешаю ход...»)
  тречатся через `_track_pending_combat_message(session_id, message_ids, chat_id)`.
- `_cleanup_pending_combat_messages(session_id, bot, chat_id, delay=1.0)`
  вызывается **строго в конце** `_send_combat_turn_result` — после того как
  нарратив полностью отправлен (включая multi-chunk blockquote и кнопки
  перевода). Это ГАРАНТИРУЕТ, что тех. сообщения исчезают только ПОСЛЕ
  нарратива — без race conditions с таймерами.
- `auto_delete=15` убран из боевого пути; оставлен только для non-combat
  «✅ сходил» (там нет долгого ожидания LLM).

Этот паттерн — точная копия `libs/bunker/track.py` из bunker-bot: тречим
`message_id` в список, удаляем все разом после события (начала нового раунда
  в bunker-bot, после отправки нарратива — в Chacalbot).

## Симптом в реальном логе

## Диагноз (подтверждён чтением кода, не только логом)

Три независимых дефекта, усиливающих друг друга:

1. ГОНКА РЕЗОЛВЕРОВ. Боевой цикл (ход NPC `_resolve_npc_combat_turn`, ход
   игрока `_resolve_pc_combat_turn`), dual-narrative
   (`resolve_non_combat_round`) и обычный раунд
   (`resolve_round_master_only`) вызывали Мастера ПАРАЛЛЕЛЬНО — каждый со
   своим контекстом, своими костями и своим мнением об HP. Особенно
   неприятно: КАЖДОЕ сообщение игрока во время хода NPC порождало СВОЙ
   auto-resolver (`_auto_resolve_npcs_then_pc` был без single-flight
   guard), а каждая подача non-combat-действия — СВОЙ fire-and-forget
   `_resolve_non_combat_round` (create_task без координации).

2. LOST UPDATE СЧЁТЧИКА РАУНДОВ. `advance_round()` делал
   read-modify-write двумя отдельными SQL-запросами
   (get_meta → +1 в Python → set_meta). Параллельные резолверы читали
   одно и то же значение и писали одно и то же «+1» — отсюда дубли
   ([Раунд 2] дважды) и прыжки номеров.

3. НЕПРАВИЛЬНАЯ КЛАССИФИКАЦИЯ ИГРОКОВ. `start_combat_for_participants`
   сопоставлял имена участников из tool-call Мастера с персонажами ТОЛЬКО
   точным `name.lower()`: любое отклонение имени в нарративе («Храфна
   Морвен» вместо «Храфна», @username) превращало ЖИВОГО ИГРОКА в
   NPC-комбатанта с player_id=0 → бот считал его «не в бою» → его ходы
   уходили в параллельный dual-narrative резолвер → гонка из п.1.

## Фиксы

### 1. Session-wide резолвер-мьютекс (главный фикс)
- `BaseSessionMixin.get_resolver_lock(session_id)` + `is_resolver_busy()`.
  ЛЮБОЙ вызов Мастера для сессии держит этот лок: в каждый момент времени
  у сессии существует максимум ОДИН активный нарратив.
- Под локом теперь работают: `resolve_round_master_only`,
  `resolve_non_combat_round` (тела вынесены в *_locked), ход NPC
  `_resolve_npc_combat_turn` (контекст → Мастер → отправка нарратива) и
  ход игрока `_resolve_pc_combat_turn`.
- «Параллельно» для dual-narrative теперь значит «не дожидаясь конца
  боя», а НЕ «одновременно с боевым ходом»: действия копятся в очереди и
  разрешаются следующим пакетом сразу после освобождения лока.
- Бонус: даже если будущий код забудет лок и дважды запустит резолв —
  второй запуск выйдет по «No queue state» (первый уже очистил очередь),
  а не наделает параллельных нарративов.

### 2. Атомарный счётчик раундов
- `Database.increment_meta(key, default)` — инкремент ОДНИМ UPSERT-
  стейтментом (`ON CONFLICT ... CAST(value AS INTEGER) + 1`) в одной
  транзакции; SQLite держит блокировку записи до коммита, вклиниться
  между чтением и записью невозможно. `advance_round()` переведён на него.
- Нечисловое старое значение («banana», битая запись после падения)
  CAST-ом трактуется как 0 — счётчик самовосстанавливается.

### 3. Single-flight auto-resolve NPC-ходов + честное сообщение ожидания
- `_auto_resolve_npcs_then_pc` получил флаг `_auto_npc_resolving`
  (libs/handlers/_state.py): второй триггер, пока резолв идёт, просто
  выходит — дубликаты резолверов невозможны.
- Во время хода NPC игроки в бою больше НЕ спавнят авто-резолв своими
  сообщениями. Вместо этого — требуемое поведение: бот пишет
  «⚔️ Ход {стражник}. Игроки в бою не могут действовать — ожидайте.»
  (в обеих ветках _process_dn_action: с очередью и без).
- Если боевой цикл умер (рестарт/ошибка) — он оживляется одним таском
  (`_active_combat_loops` guard), а не по одному на каждое сообщение.

### 4. Игроки корректно добавляются в бой
- Новый `match_participant_to_character(name, chars, players)` в
  combat_coordinator.py: точное имя (casefold) → @username/display_name
  игрока → нормализованное имя (без пунктуации/регистра) → покрытие
  токенов ≥ 0.5 и однозначное («Храфна Морвен» → «Храфна» ✓;
  «Воин с мечом СЛИЗЬ» → «СЛИЗЬ» ✗ 0.25 — монстр с именем игрока внутри
  больше НЕ притягивается к персонажу, регресс BUG #3-семьи закрыт).
- Подключён в ОБА пути старта боя: `start_combat_for_participants`
  (V10b, основной) и легаси `start_initiative_combat` (dechrauymladd,
  с сохранением легаси-фолбэка на player_map).
- Комбатант игрока теперь всегда получает каноническое имя персонажа и
  настоящий player_id → `is_non_combat_player` больше не misклассифицирует.

### 5. Non-combat очередь переживает конец боя
- `end_initiative_combat` больше не зовёт `clear_non_combat_queue`
  (раньше комментарий обещал «разрешим в следующем обычном раунде», а
  код действия ТЕРЯЛ). Остатки подмешивает к первому же обычному раунду
  `resolve_round_master_only` (merge в player_actions; если игрок уже
  подал действие в основной раунд — берётся оно, остаток не дублируется).

## Баг 1: «⏭️ не ответил вовремя — ход пропущен» при том, что игрок УСПЕЛ

Две независимые дыры давали один симптом:

1. **Отложенный резолв игнорировал бой.** Когда игрок подаёт ход в бою,
   а DB-бот ещё обновляет мир, резолв откладывается (mark_pending_resolve).
   После завершения обновления мира («✅ Мир обновлён…») отложенный ход
   ВСЕГДА шёл через обычный `_resolve_and_send`: нарратив приходил
   («нарратив двигается»), но инициатива НЕ сдвигалась и боевой цикл не
   перезапускался. Через 5 минут таймер auto-skip будил себя и писал
   «не ответил вовремя», хотя игрок успел.
   - `engine._route_deferred_resolve()` — чистая функция маршрута:
     свежий combat_active + действие из очереди →
     `("combat", action)` → `_resolve_pc_combat_turn` (сдвигает
     инициативу, перезапускает боевой цикл); вне боя → `("normal")`
     как раньше; пустая очередь (бой закончился во время обновления) →
     `("skip")` + честный новый сбор действий.

2. **Таймер auto-skip не отличал «ход не сдвинулся» от «НОВЫЙ ход того же
   игрока».** Проверка была `current.player_id == player_id`: в соло-бою
   (или быстром круге инициативы) раунд заворачивался к тому же игроку
   за пределами 5 минут, и СТАРЫЙ таймер убивал СВЕЖИЙ ход с тем же
   сообщением «не ответил вовремя».
   - `_setup_pc_combat_turn` фиксирует токен хода
     `(round_number, current_turn_index)`; `_auto_skip_turn` при несовпадении
     токена просто выходит (stale timer).
   - Watchdog-самолечение: если игрок действие ПОДАЛ, а резолв потерялся
     (падение/рестарт) — таймер перезапускает боевой резолв вместо скипа.
     Сообщение «не ответил вовремя» теперь появляется только когда игрок
     действительно молчал весь таймаут.

## Фикс 1: `_extract_json_object` (db_bot_engine.py)

Устойчивое извлечение JSON-объекта из ответа модели, 4 стратегии:
1. прямой `json.loads`;
2. срез первого `{` … последнего `}` (лечит прозу вокруг JSON);
3. срез + удаление висячих запятых (`{"hp": 12,}` → валидный JSON);
4. срез + `ast.literal_eval` (одинарные кавычки, True/False/None).

Все 5 гардов парсера (пустой лист, <10 символов, error-маркер, имена-плейсхолдеры,
болванка без расы/класса/навыков) сохранены без изменений — усилен только
АРХИВ ответа модели. При неудаче всех стратегий в лог пишется head+tail
сырого ответа (диагностика без доступа к серверу).

1. **Реестр + отмена.** Все генеративные функции движка обёрнуты декоратором
   `@generation_task`: резолв раунда (`_resolve_and_send`), non-combat lane
